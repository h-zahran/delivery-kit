# Feature Specification: Phase B records config before the base suite starts

**Feature Branch**: `056-suite-base-config-order`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "SKILL.md phase B runs `progress.sh suite-base <feature> start`, but no text says to record `config` in the state file first. Without it the command prints "base suite not started: config.testCommand is not recorded" and exits 0, so F.5 loses its citation and runs the full suite (about 6 min). Make B say to record `config` before that command, and add a test that goes red if the order is swapped. SKILL.md has 362 bytes free and must stay under its size limit. Do not change progress.sh."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A run following phase B starts the base suite (Priority: P1)

An orchestrator follows the pipeline skill's phase B in the order it is written. It records the resolved configuration in the state file, then starts the base suite. The base suite starts, and F.5 can cite its result instead of running the full suite again.

**Why this priority**: This is the whole feature. Today the skill says to record the configuration but not when, so an orchestrator can reach the start command first. The command then says "not started" and exits 0, nothing stops, and F.5 spends about 6 minutes on a run it could have cited.

**Independent Test**: Read phase B of the skill and confirm that the instruction to record `config` comes before the instruction to run the start command.

**Acceptance Scenarios**:

1. **Given** the phase B text, **When** an orchestrator reads it from the top, **Then** it meets the instruction to record `config` in the state file before it meets `progress.sh suite-base <feature> start`.
2. **Given** the phase B text, **When** an orchestrator reads the instruction to record `config`, **Then** the text points to the configuration rule that says what `config` holds, and does not restate it.

---

### User Story 2 - A test guards the order (Priority: P1)

A maintainer edits phase B later, and the two instructions swap places or the record instruction drops out. A test goes red and names the fault.

**Why this priority**: The seed asks for it, and an unguarded sentence in a 65 KB document drifts without anyone seeing it.

**Independent Test**: Swap the two instructions in a copy of the skill, run the test, and see it fail. Remove the record instruction in a copy, and see it fail. Restore the file, and see it pass.

**Acceptance Scenarios**:

1. **Given** the shipped skill, **When** the test runs, **Then** it passes.
2. **Given** a skill with the two instructions swapped, **When** the test runs, **Then** it fails and names the order.
3. **Given** a skill with the record instruction removed from phase B, **When** the test runs, **Then** it fails and names the missing instruction.
4. **Given** a skill with the start command removed from phase B, **When** the test runs, **Then** it fails: it never passes on a region that holds nothing.
5. **Given** a skill where the words appear in the correct order only outside phase B, **When** the test runs, **Then** it fails: the check is limited to phase B.

### Edge Cases

- The skill's size test fails at 65,536 bytes. The file is 65,174 bytes today, so the change has 362 bytes of room, and it must leave the skill under that limit.
- Existing prose tests may pin phase B's text. A pinned span that this change moves must be regenerated by the test file's own method, never typed by hand.
- Phase C follows phase B in the file. The test's phase B region must end where phase C starts, so text from a later phase cannot satisfy it.
- Words such as "config" also appear in other phases and in the configuration section. Only the text inside phase B counts.
- A line break can fall inside either phrase. The test must read the text so that a line wrap alone does not change its verdict.
- A resume into B whose first attempt stopped before the record holds an empty `config`. The instruction must reach it, and must not overwrite a `config` already recorded.
- A `config` that holds `testCommand` as `null` reaches the same silent path. Configuration must say that `testCommand` is recorded as resolved.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Phase B of the pipeline skill MUST tell the orchestrator to record `config` in the state file before it runs `progress.sh suite-base <feature> start`.
- **FR-002**: The new instruction MUST rely on the existing configuration rule for what `config` holds. It MUST NOT add a second definition.
- **FR-003**: A test MUST fail when, inside phase B, the record instruction comes after the start command.
- **FR-004**: The same test MUST fail when either instruction is absent from phase B, or when phase B cannot be found.
- **FR-005**: For the order in phase B, the test MUST read only phase B, so text in another section cannot satisfy it.
- **FR-006**: The pipeline skill MUST stay under its existing size limit of 65,536 bytes.
- **FR-007**: `pipeline/scripts/progress.sh` MUST NOT change.
- **FR-008**: The behaviour of the base suite start command, including its message and its exit status, MUST NOT change.
- **FR-009**: The change MUST ship as pipeline 1.9.1: the plugin's changelog, its manifest and the marketplace entry MUST all name that version, and the repository's version check MUST pass. Merging and tagging stay with the owner.
- **FR-010**: `pipeline/docs/phases.md`, where it says when the base suite starts, MUST state the same order, so the two documents do not differ.
- **FR-011**: The instruction MUST reach a resume into B that holds an empty `config`, and MUST NOT overwrite a `config` already recorded.
- **FR-012**: Configuration MUST say that B records `config`, with `testCommand` as resolved. `pipeline/docs/configuration.md` MUST put the trailer write after B's record, because a write of the whole key replaces it.
- **FR-013**: A test MUST hold the start command's "not started" line and exit 0 when `testCommand` is missing, `null`, empty or not a string.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In phase B's text, the record instruction comes before the start command, with 0 occurrences of the start command before it.
- **SC-002**: Each of the 4 faults in User Story 2 (swapped, record removed, start removed, correct order only outside phase B) makes the test fail, each further fault in `measurements.md` makes its test fail, and the shipped skill makes them pass.
- **SC-003**: The skill's size test still passes, and the skill's size is at most 65,535 bytes.
- **SC-004**: The change touches 0 lines of `pipeline/scripts/progress.sh`.
- **SC-005**: The full test suite shows no new failure against the run's baseline.
- **SC-006**: The 3 version records (changelog, manifest, marketplace entry) name 1.9.1, and the version check reports agreement.

## Assumptions

- The start command's silent "not started" with exit 0 stays as it is. The seed forbids a change to `progress.sh`, and phase B already says to print the line the command prints.
- A wording change alone is enough to close the gap for an orchestrator that follows the skill as written. No new check runs at run time.
- The test belongs with the existing prose tests of the skill, and it uses their helpers for reading a region of text.
- Phase O has no release command configured, so the run itself publishes nothing. The version records ship inside the pull request.
